> **가상 예시 · Case 02 (구현 후 기록).** API·코드 경로·테스트 결과는 형식을 보여주기 위한 **가상의 기록**으로, 실제 프로젝트의 완료 사실이 아닙니다.

# C01 - 질의 분석

1. 사용자 질문을 입력받아 필요한 기록 유형을 `행동·목격`, `AI 간 대화`, `속마음`, `실험 결과`, `실험 환경` 중에서 구분하는 분석 기능을 구현했다.
   - 질문이 여러 기록 유형에 걸칠 때 검색 후보를 복수로 생성할 수 있도록 처리했다.
2. `backend/planner/planner.py`에서 실제 외부 LLM API를 호출하도록 연결했다.
   - 모델 응답을 그대로 권한 판정에 사용하지 않고, 구조화된 검색 조건 후보를 추출하는 용도로만 사용한다.
   - API 오류 시 성공한 계획처럼 반환하지 않고 실패 상태를 호출부에 전달한다.
3. 검색 대상 기록 유형과 기간 조건을 후속 검색 모듈에 전달할 수 있도록 출력 데이터를 구성했다.
   - 실제 필드 이름 및 응답 예시는 `docs/interfaces/`의 확정 계약을 따르도록 설계했다. (이 예시에서는 실제 계약 파일을 가정하지 않음)

# C02 - 기존 RAG 기능 연동

1. 앞서 구현된 RAG 검색 API의 입력, 반환 메타데이터, 오류 응답을 실제 코드에서 확인했다.
   - 후속 구현인 Planner 쪽에서 입력 구조를 맞추기로 하고 기존 RAG API 변경은 진행하지 않았다.
2. Planner 검색 조건을 RAG API 입력 형태로 변환하는 호출 로직을 추가했다.
   - `backend/planner/rag_adapter.py`에서 기록 유형 및 기간 조건의 매핑을 수행하도록 구성했다.
3. 실제 RAG 검색 API를 호출하여 `test-data` 기반으로 응답이 돌아오는 것을 확인했다.
   - 예시 테스트: `pytest tests/planner/test_rag_adapter.py -q` 실행 결과 **4개 통과, 0개 실패**. 정상 검색, 빈 결과, 필터 전달, 오류 응답을 검증했다. (가상의 실행 결과)
4. 서버의 권한 필터와 결합한 전체 경로 검증은 **미수행**이다.
   - Planner가 추출한 조건이 사용자 권한을 상승시키지 않도록 Policy Engine 및 Retrieval ACL과 함께 통합 검증이 필요하다.
   - **미완료:** PLAN 5번 오류 응답의 사용자 안내 개선은 진행하지 않았다.

> PLAN 작성이 구현보다 늦어도 관계없다. RESULT는 실제로 수행한 작업·검증 범위·남은 문제를 구체적으로 기록하며, 예시의 내용을 실제 코드나 성과로 복사하지 않는다.
